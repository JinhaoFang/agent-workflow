## 碰到的问题

每条都写了初始化技能可以怎么处理。

1. **仓库属主不对**：目标仓库的文件属于 root 和另一个用户，jh1 用 `git`、`gh` 都报 dubious ownership。用户修好后才能操作。这和本仓库建仓时的第一个问题一样。→ 探查环境时第一项就查，不能用时停下来告诉用户。
2. **依赖装在别的用户名下**：测试要用的 Playwright 浏览器装在 root 名下，jh1 跑测试有 146 个失败。补装以后全部通过。Codex 也以 jh1 身份运行，同样受影响。→ 探查环境时，用派发 Codex 的那个用户实际跑一遍验证命令，不只看配置。
3. **测试只在 CI 上间歇性失败**：回归测试偶发"体系总览页有 4 个错误"；本机连跑三遍都通过，只改文档的提交在 CI 上也会失败。`land` 合并前要跑验证，不稳定的测试会让合并随机失败。→ 探查环境时查最近几次 CI 的结果；有不稳定的测试，列为彩排 spec 的第一项。
4. **集成分支的名字对不上**：`run-spec` 按 `spec/<号>-` 找集成分支，目标仓库用的是 `integration/phase-0`。办法是先合回 `main` 作为检查点，之后从 `main` 新开。→ 检测已有的长期分支，建议先建检查点。
5. **`.gitignore` 带斜杠的规则匹配不到软链接**：目标仓库原来写的是 `references/`、`.cache/`。worktree 里这些目录是软链接，带斜杠的规则管不到，worktree 会不干净，`land` 会拒绝合并。迁移包的片段本来就不带斜杠，但没写原因，目标仓库已有的规则不会自动改。→ 自检时用 `git check-ignore` 实测一个同名软链接。
6. **第三方技能已经进了 git**：要用 `git rm -r --cached` 退出跟踪。这种提交不能按 `AGENTS.md` 的写法 `git commit … -- <路径>` 提交：只提交指定路径时，git 会按工作区的现状提交，而文件还在磁盘上。改用"核对暂存区后不带路径提交"。→ 初始化技能里写明这一步。
7. **产品技能和软链接冲突**：目标仓库的方案规定，本库将来的产品技能也放在 `.agents/skills/` 并进 git；`run-spec` 却把整个 `.agents` 软链接进 worktree。两者不能同时成立，已记进那边路线图的待定项。→ `symlinkDirectories` 的粒度只到目录，初始化技能要问清 `.agents/skills/` 里会不会有自己的技能。
8. **用户本地改过第三方技能**：目标仓库里 `to-spec`、`implement-spec` 被改成了可由模型调用，没有提交。`.agents/skills/` 下的技能 Codex 都能看到，这类改动会扩大 Codex 能自己调用的范围。→ 迁移前用 `git status` 和锁文件里的哈希查第三方技能有没有本地改动，有就问用户。
9. **原有的 `AGENTS.md` 结构不同**：要把命令手册这类内容移出去，再按 `dual-role-workflow` 加上角色一节；setup 生成的「Agent skills」一节要原样保留。→ 这一步要判断，留在对话里做，初始化技能只检查结果有没有角色一节和提交格式。
10. **产品里也有"角色"和"用户"**：目标仓库的术语里有需求方、裁判、agent，和开发协作的设计负责人、工程负责人是两套东西；术语表还规定产品里避开"用户"一词，而规则文档里"用户"指和 agent 对话的人。在 `AGENTS.md` 角色一节写明了对应关系：规则文档里的用户是项目发起人，在产品里同时是需求方和裁判；方案里的 agent 指使用本库的 Claude Code 和 Codex。→ 对齐时要问。
11. **护栏不能原样带过去**：本仓库的文档命令护栏内置 pnpm 10 的命令表，目标仓库用 pnpm 12。→ 回答路线图里"仓库级护栏要不要随行"时考虑这一点：护栏按目标仓库的工具链重写，作为那边彩排 spec 的候选，不直接复制。

12. **没读完目标仓库的设计文档就改了规则**：第一版迁移只读了方案的目录和第 7～8 节，有两处和已定的决定冲突。一是把"按定稿实现排法"划给了工程负责人，而方案第 3.6 节规定几何归体系管，spec #1 写明体系好不好由裁判人工验收、检查器零错误只是必要条件；已改为体系本身归设计负责人，工程负责人接做体系时暴露的工具缺口。二是把命令手册移出了 `AGENTS.md`，而 spec #1 的用户故事 63 要求它写在那里；保留了移出，靠 `AGENTS.md` 的指针做到"不必从代码推断用法"，已告知用户。→ 第 1 步读完方案、术语表、ADR、进行中 spec 的全文。
13. **改了目标仓库已有的命名，没先问**：方案文件名是中文且带空格，迁移时改成了 `docs/plan.md`。用户要求改回原名。→ 已有的命名和结构要改，先问人。
14. **动手前没把迁移的步骤讲给人听**：用户说了"全权负责"以后，设计负责人直接执行，用户只看到结果，事后问"迁移到底如何进行"。→ 动手前先讲要走的步骤，人确认后再开始。

没有成为问题的：

- Codex 的项目信任配置里没有目标仓库，派发照样能跑。
- 目标仓库的 `references/` 里已经有 DispatchDock v0.1.3，直接用它的安装器。
- Node 版本要求（22.18 以上）两边一致，工单脚本不用改。

### 经受住了检验的

- **`run-spec` 原样复制就能用**：技能和工单脚本一行没改，只写了 `run-spec.json` 和 `run-spec.md`，`frontier`、`link`、`dispatch`、`land`、`accept`、`cleanup` 和按批审查都跑通了。

### 问题

接着上面的编号。

15. **交接提示词里的命令没实测**：本仓库的设计负责人在交接提示词里，把实测过的"按技能名逐个恢复"简化成"恢复整个技能目录"，没再测；对齐会话原样写进工单。执行会话动手前在临时 worktree 里实测，发现会删掉进 git 的 `run-spec`、带回已移除的旧技能，改成按 `skills-lock.json` 逐个恢复。→ 交给下一个会话的命令，交实测过的原文。
16. **环境前提是推测**：对齐会话把"CI 机器 4 核"当事实写进 spec，私有仓库的 GitHub runner 实际只有 2 核。Codex 按 4 核在本机试了约 6 分钟复现不出来，按工单预留的退路改到 CI 上诊断才查清。→ 写进 spec 的环境事实先测（例如在 CI 上打印一次核数）；测不了的标明是推测，并给退路。15、16 两处都靠工单里要求实测的验收项和预留的退路拦住。
17. **对齐时技术性的取舍没讲白**：第一轮问题里，"不稳定测试怎么算修好"附了三种做法和 Actions 时长，用户按推荐通过后又问"CI 这里不理解"。补讲现状时，设计负责人自己发现原来的标准（CI 连跑 10 次）证明不了修好，改成先在本机复现再修。→ 要人拍板的问题涉及技术现状时，先用白话讲现状再问。
18. **派发指令写死"不要推送"**：有的验收要 CI 运行链接，而 CI 只在推送后运行。这次在补充说明里临时放开。→ 工单能声明允许推送自己的工单分支。
19. **`land` 在 rebase 后不重装依赖**：#37 新增了依赖，后合并的 #38 验证必然失败，设计负责人手动在 worktree 里重装。→ rebase 改动了锁文件时，先运行安装命令。
20. **远端分支没人删**：推送过的远端工单分支，`cleanup` 不删；`cleanup` 在 PR 合并之前运行，集成分支合并后也没人删。两个仓库原来都没开 GitHub 的"合并后自动删除分支"，已打开，并补进开局清单。→ `cleanup` 删除远端工单分支。
21. **最后一批的审查和收尾审查重合**：执行会话自行合并成一次。→ 写进 `run-spec` 第 6 步。
22. **审查的用量没有记录**：工单派发的用时和 token 由 `accept` 自动写进验收评论，审查的没有。写汇报时要去 `~/.codex/sessions/` 翻，还要自己加上审查开的子代理。→ 审查结论的评论自动附上用量。
23. **派发时做的决定只在本机**：派发 #38 时，"`node` 后的路径按是否进 git 判断"这个决定写在补充说明文件里，返工单 #39 修的就是它漏掉的另一半（文件还要实际存在）。`cleanup` 以后，这个决定只留在汇报里。→ 派发时临时做的决定，同时评论到工单上。
24. **验证步骤在 4 份文档里各列一遍**：`AGENTS.md`、命令手册、工作流总图、`run-spec.md` 都写了 `pnpm verify` 有哪几步。三张并行工单各加一步，每张都改这几份文档，最后合并的一张在 6 个文件上冲突，其中 3 个是文档。这个写法是从本仓库带过去的，本仓库的 `AGENTS.md` 也一样。→ 步骤只在步骤表和命令手册里列，其他文档写指针。

## 真实使用：spec #1 第 0 阶段

彩排以后，design-system 用安装版的 `run-spec` 跑完了真实的 spec #1（2026-10-12 22:11～10-13 16:25），用户审 PR #55 后又在另一个会话里返工（10-13 18:04～21:50），PR 已合并。证据来自两次会话的记录（`~/.claude/projects/-root-project-design-system/` 下的 `7f9795da…`、`3818ba85…`）、那边的汇报 `docs/reports/spec-1-phase-0.html` 和 git 历史。

### 经受住了检验的

- **工单脚本**：两次会话里 `dispatch`、`land`、`accept`、`link`、`review`、`cleanup` 反复使用，都跑通。`land` 两次停在 rebase 冲突，按提示解决后重跑即可；一次验证失败暴露了两张工单叠加才出现的问题，退回返工。
- **按批审查**：三次审查共发现 12 条，其中 4 条是设计负责人自己做的部分违反了自己写的规则。
- **定稿先行**：返工时设计负责人先做可操作的原型和规则说明，Codex 照着实现，三轮后通过，用户点名肯定。
- **先给用户看方向**：返工时孔版印刷的样张内容先交用户确认，一次通过，成品是用户评价最高的一件。

### 问题

接着上面的编号。

25. **`role:design` 的工作交给了子代理**：12 张体系工单迁移时没有执行角色，执行时一次全标成 `role:design`。量太大，设计负责人自己建 worktree，开了 4 个 Claude 子代理去做（每个的任务通知报 32～39 万 token），4 次撞上额度上限、2 次卡住，约 5 小时停摆；用户两次问"为什么是你在写代码"。规则其实写了：角色文档开头写着"量大、能写清楚的执行交给工程负责人"，`dual-role-workflow` 的描述写着"把大部分 token 花在 Codex 上"，`run-spec` 写着"在主工作区自己做"。但同一份角色文档的分工清单把整套体系都列进"自己做"，清单比原则具体，agent 照清单做；"自己做"没说子代理算不算，全局规则又允许自行委派。→ `run-spec` 第 3 步写明 `role:design` 在主会话亲手做、一次一张，量大就把方向写进工单派出去，子代理只准备供判断的材料；`setup-run-spec` 核对分工按决定和体量分、清单和原则说法一致；迁移时和用户一起给进行中的工单定执行角色。
26. **难回头的方向没给用户看**：用户授权设计负责人代行裁判验收后，两套新体系的方向由设计负责人从方向稿里自己挑，三套体系共用一份内容。用户到 PR 才看到：6 条意见、9 张返工单，一套体系整个移除。→ `run-spec` 写明难回头的方向决定在实现前给用户看，代行只管成品。
27. **写了的规则没被读到**：生图规则在迁移时就写进了那边的 `docs/workflow/README.md`，执行会话直到收尾更新路线图才第一次打开这份文档。角色文档指向它的两句话，一句是"整体流程见…"，一句讲交给裁判的预览，都不会在做图像时被想起。孔版第一版由 Codex 用代码画人物和望远镜，Codex 没有生图接口，验收两轮也没挑出来。→ `run-spec` 第 3 步要求开工前按角色文档的指针读这类工作的规则；`setup-run-spec` 核对指针按触发条件写。
28. **教训只进了本机记忆**：用户在返工会话里讲的工作方式（定稿先行、样张内容先确认），设计负责人写进了 Claude 的本机记忆，规则文档里没有。Codex 和别的机器上的会话都看不到。→ `run-spec` 写明执行中的工作方式反馈写进规则文档或路线图待定项。
29. **参考文档难读、易冲突**：那边的命令手册 54 行，最长一行 1,971 字，spec #1 期间 18 次提交改它。派发补充说明反复写"只加自己那一项"，两次 `land` 冲突都在它身上。→ `setup-run-spec` 建议按需读的参考文档一条事实一行、按主题分节；那边的命令手册在 design-system 的改进里拆。
30. **没有"PR 审查后返工"这条路**：`run-spec` 写到开 PR、交汇报就结束了。返工会话即兴处理得对（返工单挂原 spec、同一集成分支、审返工范围、更新 PR 正文），但汇报里的 KPI 是手算的、时间线坐标写死，补数据时数错、画出了框。→ `run-spec` 第 7 步补上返工的做法；`report.md` 要求数字和坐标从数据数组算。

74. **汇报靠表格**（用户提出）：spec 汇报给人读，用户觉得好用，但数字、对比、时间、结构多用文字和表格。spec #194 的汇报有 13 张表、没有一张图。→ 时间用时间线，用量和数量对比用条形图或折线，结构和数据流用结构图或流程图；表格只留给逐项查找的清单。汇报模板随技能提供。
75. **执行会话依附终端**（用户提出，10-29 执行 v3 时）：前台的 Claude Code 会话要一直开着，关掉终端可能连带中断派发出去的 Codex。Claude Code 有后台会话：`claude --bg` 启动，`claude attach` 进入，离开后继续运行，`claude agents`、`claude logs` 查看。→ 用户要求写进 v3：作为可选的启动方式写进 setup 第 6 步的交接和本仓库的工作流文档；权限模式要和平时一致，否则碰到确认就停下等人。

## v3 的第一次工程实测：PathJX #208、#209

2026-10-30，PathJX 用 v3 在一个设计负责人会话里跑完 spec #208（规则与文档整理）和 #209（推理代码去重）：约 10 小时，21 张工单（6 张设计、15 张工程），Codex 运行 26 次。设计负责人主会话缓存读取约 1.10 亿 token，Codex 输入约 1.61 亿。派发前的独立审查提出 12 条必须先改的问题（例如 GPU 锁在不同检出目录下会变成互不排斥的几把锁），3 个 Codex 并发排队、`land` 推送失败后重跑续做都按设计工作。下面是暴露的问题，改法进 `workflow-v3.1`（spec #94）。

80. **目标没人验收**（用户审 PR 时发现）：独立审查、逐张验收、收尾审查都只核对"做的是不是 spec 和工单要的"。#208 的问题陈述是"6 个结果平均出现在约 19 处，新会话开工要读约 188 KB"，汇报没有重测，只写"读的东西少了"。spec 自己要求补写两份汇报、逐条处理 148 处引用，变成新的 Markdown 文件；文档链接检查让每份文件都挂进索引，"被链接"看起来像"需要"，Codex 的逐份盘点也据此建议几乎全部保留。用户指出后返工删了 42 份过程文档（约 726 KB）。→ spec 的问题陈述给出可复测的现状，收尾按同一口径重测并写进汇报；独立审查查"有没有用户故事和目标相反"；过程文档是验收产物，不进文档目录，被链接不是保留的理由。
81. **`accept` 不核对合并**：#211 把 `land … | tail -6` 和 `accept` 串在一条命令里，管道吞掉了验证失败的退出码，工单被以通过关闭，事后重开更正。第 66 条只解决了 `verify` 本身。→ `accept --result 通过` 核对提交已在远端集成分支上；只读工单显式声明没有提交。
82. **验证环境不在配置里**：每次 `land` 和 `verify` 都要带 4 个环境变量（浏览器路径、端到端时限、测试进程数、Go 并行数）。上下文压缩后会话记不得，翻自己的会话记录才找回。→ 执行配置加验证环境，用 `{mainRoot}` 代替机器路径。
83. **并发时完整测试互相干扰**：3 个 Codex 各自跑完整测试，加上 `land` 的验证，端口池耗尽（#214 的合并被挡住），默认 24 个测试进程下网页端到端测试反复超时（#211、#231、PR #228 的本机 CI）。仓库规则写了"两套完整测试错开运行"，但 Codex 看不到别的运行。→ 可选的验证排队：同一仓库的完整验证一次一套，Codex 也经 `verify` 排队。
84. **保留目录装满验证副产物**：路线图「待定」的这一条坐实了。14 张工单的保留目录共 1.5 GB，每张约 100 MB，几乎全是 `.venv` 里的字节码、pytest 和 ruff 缓存、构建产物、测试输出，真正的验收证据另有复制。→ 可选的"可直接删除的被忽略文件"模式。
85. **新 worktree 装依赖靠外网**：PostgreSQL 下载的 SSL 连接至少中断 4 次，每次手工把主工作区的版本硬链接进去再重派。属于 PathJX 的安装命令，在 PathJX 修：安装复用主工作区已校验的下载缓存。
86. **v3 的汇报模板不如以前**（用户提出）：模板把"图优先"当成了目标，放了累计输出折线、按处理方式分组的条形图、每次都一样的分工流程图，和上一个 spec 比用量（没有意义）；交付和结果被挤到页面后半。用户指定以 PathJX spec #27 的汇报为底：任务、交付、结果在前，表格清单、可折叠明细、数据口径与缺项。→ 模板和写法以它为底重做，图只用在比文字和表格更清楚的地方，用量照报但不和以前比。
87. **一个会话跑两个 spec**：主会话压缩两次，用量没法按 spec 拆开；6 张设计工单里根 README、路线图这类标准写得清楚的改写本可以派给 Codex。还有两处行为失误：没经批准删了一个已合并的本地分支，一次向用户提的问题写成了英文。→ 不改流程，记在这里：一个会话一个 spec 更容易核算；标准清楚的改写照第 3 步派出去。

## 给人看的产出：v3.1 核查报告的反馈

106. **把实现位置的自主权写成了所有路径禁令（C01）**：工单约定说“spec 和工单都不写文件路径”，角色模板却要求定位定稿，实际 #6 也指定验收产物。根因是把实现文件清单和输入、交付定位混在一起。思路 3 已能覆盖，无需新规则：比较完全取消限制与准确区分两类信息，选后者。修改现有一句话，参照和产物准确定位，实现位置交执行者判断。实现验证：源模板和三个消费仓库自有约定已按定稿修改，静态或文档专项检查通过；消费端 PR 待合并。用过后看工单能否找到定稿、有无不必要地锁死实现位置。
107. **报错标记替代了授权判断（C02）**：技能正文第 4 步把所有“出错：”都交用户决定，但角色已授权常规实现与恢复判断。根因是按工具输出而非操作影响划边界。思路 2 已覆盖：保留失败报告和状态核对，在既有授权内恢复；范围、费用、权限或难回头的决定变了才请用户。比较增加错误分类清单与改现有原则，选改一句话。实现验证：已改现有步骤，保留失败报告与状态核对，没有增加错误分类表。用过后看常规恢复是否仍额外打断用户、有无越过授权。
108. **派发前独立审查是否启动由用户选择（D02，用户决定）**：现行角色模板按任务类型强制触发，消费仓库有的没有同步。用户本次明确这不是每个任务或 spec 的必经关卡。保留 `review-spec` 能力，现有步骤改为用户选择后执行；角色指向同一约定。比较补齐强制触发与改为可选，按用户决定选后者。实现验证：源技能、角色模板及四仓库角色或流程图已按用户选择触发同步；本 spec 未强制启动派发前审查。用过后看未选择审查时是否仍被挡住、选择后的处理是否完整。
109. **技能已经升级，消费仓库的自有文字仍教旧做法（D01、D03—D05、G01）**：三仓本机技能与 v4 一致，design-system 仍让父 spec 读评论、收尾改路线图进度；三份工程角色缺推送例外；PathJX 配置说明仍教手拼挂单和续做；design-system 把聊天语言写成仓库规则。根因是技能源码与每仓生成文档分别维护。修在各自仓库，方法模板只保留当前约定，不增加逐字同步检查。思路 3 区分当前决定、历史、个人偏好；结果回到各仓库 PR 核对。实现验证：video-studio#117、design-system#91、PathJX-01#252 已准备自有文档 PR，锁文件与技能安装均未改。前两仓静态检查通过，Path 文档专项通过，整仓检查仍受离线 Go 缓存阻挡。用过后看是否再出现文档与派发冲突。
110. **暂缓清理只保护本地分支，远端仍删除（D06）**：`cleanup` 的 `retained` 集合只过滤本地分支，远端循环没有应用。脏、当前使用或分支状态异常的工单现场应暂缓清理，正常工单照旧。比较只改提示与让两端共用保留条件，选后者，用现有临时仓库 CLI 接缝验证组合行为。实现验证：cleanup CLI 12 项通过，覆盖脏状态、当前与主工作区、分支不符、缺路径和正常清理。未对真实工单执行清理。用过后看异常工单两端是否都保留、其他 spec 是否不受影响。
111. **嵌套验证把包装调用与实际执行重复累加（E01）**：`pr-check → verify` 已受支持，两个包装各写台账；现有评分表逐行累加。固定输入可确认，当前 14 行生产台账没有嵌套样本。比较显式包装开关、时间重叠去重、独立事件流和可选父调用身份；选父调用身份，保留包装行、实际执行分别计数，不猜旧记录关系。排队和 land 调用仍按调用记录保留。实现验证：CLI 已覆盖嵌套一次、多子调用、真实并行、失败、锁开关、排队、旧新记录与仓库隔离；本轮只确认机制，不外推业务分层效果。用过后看真实一次验证是否计一次、多子调用和真实并行是否仍分别计数。
112. **审查索引为读第一行而读完整历史文件（E04）**：`review` 用完整读取再截第一行，本机索引范围约 3.2 GB；无关坏文件也混入本次缺数理由。根因在读取实现和诊断范围，不需要 agent 行为约束。比较全文缓存与首行流式读取，选后者，关联后才读取目标全文；未知归属诊断仍保留，和本次会话缺数分开。实现验证：review 15 项通过；收尾复核后补了无换行坏文件的内部读取预算，16 GiB 稀疏文件测试保留已知用量并输出扫描限制。用过后看读取范围是否限于元数据和关联会话、告警是否如实限定。
113. **辅助工作未归属便既不统计也不标缺数（E05）**：#6 的 `check-6-2` 完成 12.9 分钟、输入 1,505,004 token，报告已披露但评分表只认工单和审查名。用户选择辅助工作也纳入。比较限定统计口径、强制开工单、改第三方派发器和显式补录关联；选可重复 `scorecard --record`，正常执行持久关联，dry-run 仅预览，重跑和 cleanup 共用。辅助类别如实显示，不伪装审查；缺记录列缺数，关联不扩大删除授权。实现验证：本轮准备研究和跨仓同步的辅助派发已实际关联，重跑不带参数数据一致；CLI 覆盖新关联旧文件与缺记录。收尾发现移址 worktree 漏保护，已改为共用实际删除清单，返工回归和独立复核通过。用过后看辅助工作是否计入、重跑不带参数是否记得、旧评分表是否会漏过新关联。
114. **迁移记忆仍被当作当前续做计划（F01）**：本机 `pathjx-skills-migration.md` 的 Ongoing 和最后 Next 仍指拆 #2、发布 v4、切换三仓，权威路线图已记完成。根因是历史快照同时承担进度入口。比较追更整份历史与改历史定位，选后者；保留出处，当前状态只指路线图和打开的 spec，不新增第二份进度表。实现验证：本机记忆描述、How to apply 和索引已改为历史追溯与权威入口，保留原有日期和证据，不追更历史进度。用过后看新会话是否仍提议重复迁移。

## pstack 对照后的修正（spec #22、#23，与核查修复一起发布 workflow-v5）

2026-11-05，用户要求结合 pstack 批判性、有选择地借鉴，保持流程灵活、可插拔；确认的一项是像 pstack 一样灵活分配各角色的 agent 框架和模型。对照结论和三种处理方式见 `pstack-notes.md`。

115. **角色和工具绑死**：流程把"谁负责"和"用什么跑"写成同一件事，全流程清点出 182 处耦合（身份文字 39、脚本行为 50、配置项 44、数据来源 42、汇报模板 7）。后果已经出现：spec #16 的主会话在 pi，评分表主会话四项全空；10-26～27 Claude 额度用完时 Codex 代任设计负责人；派发不能按席位或工作类型设模型；"工程负责人看不到设计技能"靠目录巧合，换框架就失效。思路 3 能回答配置放在哪（工作类型的词表属于仓库，用哪个框架和模型属于个人和本机），思路 2 支持派发时临时改，缺的是机制。比较三种做法：只改文字，换框架仍要改代码；照搬 pstack 的规则文字，跨框架无效、也无法校验；席位配置加每个框架一个适配器，脚本解析、`doctor` 报来源、记录实际值。选第三种。派发层的接法（自建、Codex 照旧其余自建、给上游贡献）用户选自建；用户补充按工作类型选模型（pi 接多个提供商，前端用 zai/glm-5.3-flash，后端用 openai/gpt-6.1-sol）。用过后看：换框架和模型是否只改配置；评分表能否按模型比较返工和用时；技能隔离在三个框架下是否成立。
116. **验收怎么测，每次重新摸索**：第 102 条的汇报检查每次现写、量法恒为零也没发现；video-studio #67 为逐帧证明跑了约 3.3 小时，没有"做到什么程度就够"；design-system 总览页 4 个错误的根因未锁定。根因是仓库没有持久的"怎么驱动真实产物、什么结果算证明"的入口，思路 1 的同一口径重测缺载体。比较：每张工单各写测法（重复劳动、口径会漂）；pstack 的验证技能加 feature map（生成项目自己的验证技能，按功能写入口、驱动步骤和可观察的结束状态，生成后必须实跑）；不加。选第二种并改造成自己的（生成位置、去掉 Cursor 依赖、接 setup 和【实测】），先在本仓库为汇报生成一个试用。用过后看：【实测】是否引用功能编号，同类检查是否不再现写，量法能否分辨好坏。

第 95、99、103 条，pstack 分别提供了可比较的做法（盲化对照、成果即时外化、追踪真实消费者），本版不做，下一版评估时作为候选，见 `pstack-notes.md`。
