# 五条思路

执行 spec、写规则、把东西交给人看的时候，都按这五条判断。步骤里写"按思路 N"的地方是最常用到它的时候；步骤没写到的情况也照它们推断。每条末尾列出替你做了一部分的机制，用法见技能正文和 `--help`。

## 1. 验收回到原问题

做完不等于解决。收尾时，按 spec 问题陈述里的现状用同一口径重测；没达到的开返工工单，或者写进 PR 和汇报。开工前也用这个口径看：问题陈述有没有可复测的现状，工单做完会不会让结果离目标更远。

- **为什么**：PathJX 第一阶段的 13 个 spec 都没有核对目标，工单全关了就算完成。v3 起收尾时复测，#208 的 7 项只达成 4 项。
- **例子**：问题陈述写"#233 至少跑了 18 次完整验证"，收尾就数本 spec 的完整验证次数和分钟数，不写"已加测试分层"。问题陈述没有可度量的现状时，写明用什么判断目标达成。
- **机制**：`review-spec` 的审查重点、第 7 步的目标核对。

## 2. 每个节点重新判断资源和做法

开工时排好的顺序会过时。作业结束、名额空出、结果出来时，重看名额、远端状态、机器负载和剩下的工单，再决定下一步：并行还是串行，用什么工具，谁来做。换不换都写一句理由。

- **为什么**：计划时看不到的情况在执行中才出现：账号同时只能跑两个 Codex，第三个被拒；审查和派发抢同一批名额；设计工单没推送就写验收评论，被脚本拒绝。
- **例子**：一张工单的派发结束了，先看这一批该不该审、审查要的名额有没有（审查不经过派发队列）、集成分支推送了没有，再派下一张。量大的调研和数据查看派给调研席位，子代理只做小而急的只读查找。会话也是资源：里程碑处可以交接到新会话；几个设计会话同时工作时各用自己的 worktree，主工作区留给正在执行的 spec。
- **机制**：`dispatch` 的并发排队、`slots`、验证锁（`exclusiveVerification`）、按需的 `watch`。

## 3. 规则按"换一个人或一台机器接手，这条还必须成立吗"归类

新加一条规则、归类用户的反馈、升级时整理已有规则，都先问这一句。答案决定它放在哪，也决定它要不要写成文字：能机械判断的做成脚本或检查，脚本已经覆盖的删掉文字。

- **为什么**：规则堆在一起，agent 每次都要读完；个人习惯、本机的坑、一次性的数值混进仓库规则，换人换机器就成了错的。
- **例子**：五类归类，加一类可删除。

  | 类 | 判断 | 放在哪 |
  |---|---|---|
  | 仓库规则 | 项目规范和防止项目变乱的约束：产物、流程、验收、协作，不论谁提的、带不带日期 | `AGENTS.md`、角色文档、配置说明 |
  | 现场参数 | 随现场调整的数值和开关（并发名额、超时、磁盘余量） | 只写一处（配置或一份文档的一节），规则只写原则并引用它 |
  | 本机说明 | 只在某台机器上成立、修法也只对它有意义（工具路径、PATH 顺序）；"本机 CI"在每台机器上都适用，不算 | 开发环境文档里按机器分的一节 |
  | 个人偏好 | 只关系到某个人和 agent 怎么对话（聊天语言、讲多细、会话长度）；写进仓库的书面产物不算聊天 | 那个人自己的配置 |
  | 记录 | 历史实测、证据、当时为什么这样定 | 日志、研究目录、ADR，规则里最多留一句指针 |
  | 可删除 | 脚本、检查、工具默认行为已经完整覆盖 | 删掉文字 |

  同一个问题延伸到事实放在哪：每个事实只存一处，别处链接。结果数字只写一处；spec 的修订直接改正文、末尾记修订记录，评论只留摘要（派发时执行者只读父 spec 正文）；路线图只放目标、已定、下一步和待定，进度看打开的 spec；草稿、工作表、回执、核验记录是验收产物，要留的结论并进现有文档，被链接不是保留的理由。两处说法冲突时列给用户裁决。
- **机制**：`setup-run-spec` 的篇幅比较（生成的规则合计不超过上一版）、`doctor` 报告配置的实际值和来源。

## 4. 给人的产出按人的读法设计

agent 读文字快，人不是。交给用户的东西（汇报、要批准的清单、要确认的草稿、对机制的解释）先放要用户做的和结论；要读者记住数字再比较的地方画图；证据（实测数值、截图、命令输出摘要）放在结论旁边，GitHub 链接只作补充；明细折叠。写给没参加讨论的人：用内容指代，不只写编号，写清看了什么；提问附白话解释、选项和推荐。

- **为什么**：用户按六点给汇报打分（做了什么和效果、目标与证明、要用户做的、证据能否抽查、代价与时间、风险与遗留），v3 和 v3.1 的证据只把"证据"两个字链到 GitHub，阅读时间从约 10 分钟变成约 15 分钟。核查报告靠长表格，用户读完没看懂"验证锁"。
- **例子**：`cleanup --dry-run` 列出 67 行路径时，先写"派发记录 6 份、验收产物 4 个目录共 3 MB、分支 5 条"，明细写进文件给链接。要用户确认的规则草稿，先给每类多少条、比上一版增删了哪些、哪几条冲突，全文作附件。解释验证锁时画一张谁在等、谁先跑的图，再写一句没有它会怎样。
- **机制**：汇报模板（`report.md`）、评分表（汇报的图直接用它的数据）。

## 5. 验证范围跟着改动的影响走

跑多少验证由改动能影响什么决定：只改文档的只跑静态检查；开发中跑相关测试和静态检查；合并时按改动跑一次，改了代码的是完整验证；spec 收尾再跑一次全套。开工前先确认基线是绿的，免得并行的工单各修一遍同一个既有失败。

- **为什么**：PathJX #233 的 183 分钟里有 119 分钟在跑完整验证或排队，只改文档的工单也跑了全套。更早有三张并行工单分别修了同一个既有失败。
- **例子**：设计工单只改了技能正文，`verify` 按改动路径判断，只跑静态检查。执行者改了派发脚本，开发时跑派发的测试和静态检查，完整验证留给 `land`。
- **机制**：`verify` 和 `land` 按改动路径选层、验证台账、`pr-check`。
