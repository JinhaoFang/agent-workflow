# 验证入口

验证入口回答"怎么证明它真能用"。有了它，【实测】照着启动、驱动、取证，测到什么程度就够由功能页的结束状态决定，不用每次现场摸索。读者是下一个冷启动的执行者，它没见过这个产物，所以每一步都要能照抄。

位置固定在 `docs/verification/<产物>/`，进 git：`README.md` 写怎么跑，`features/` 每个功能一页，带的脚本放同一目录。它不放进任何框架的技能目录，各框架都按路径读；仓库 `AGENTS.md` 用一行指向它。一个仓库有几种产物（页面、命令行、服务、视频）时，每种一个目录。

## 生成

1. **先看仓库，再问人。** 从代码和文档回答下面五件事，只问看不出来的：
   - **产物**：用户实际碰到的是什么，页面、命令行、服务还是文件。几种都有时先做主要的一种，其余记下。
   - **启动**：仓库自己写的启动命令、端口、环境变量、种子数据、登录。
   - **驱动**：先找现成的驱动办法（已有的浏览器测试、命令行包装、能直接请求的接口），没有再选通用做法：页面用无头浏览器，命令行用独立的终端会话，服务用 HTTP。
   - **取证**：能留下什么，截图、终端记录、响应正文、日志、退出码、写下的文件。
   - **隔离**：两个实例能不能同时跑。不能就写明，宁可拒绝驱动共享实例，也不弄坏别人的现场。

   当前检出跑不起来时，先修好或准确报告，再往下写；照着坏的基线写出来的步骤是错的。

2. **写 `README.md`**，每节都来自上一步实际查到的东西，不留占位：
   - **启动**：确切命令，以及怎么判断它好了（某行日志、端口应答、提示符）。短命的命令行没有常驻进程，启动就是构建一次，每次驱动开一个独立会话。
   - **自检**：一条只读检查，回答"这个实例值得驱动吗"：进程在、版本对、端口是自己的。驱动前先跑它，出了意外再跑一次。
   - **驱动**：用这个仓库真实的选择器和命令，优先稳定的抓手（无障碍名称、数据属性、提示文字、路由），不靠坐标和顺序。
   - **取证**：取什么、放在哪。证明要走真实的用户路径，不走内部接口或测试专用入口；既取动作也取结果状态；能看到的之外，再核对副作用（写下的文件、插入的数据、发出的消息）。用试运行模式时，观察它实际跳过了什么（文件、网络、git 引用），不按名字推断。
   - **收拾现场**：只停这次启动的实例和临时状态，按进程号或会话名，不按程序名。证据留在本节写明的位置，收拾之后仍在。
   - **脚本**：带的脚本可以直接执行，调用方式写在正文里。

3. **播种功能地图。** `features/README.md` 写共同的前提、驱动约定和取证要求，再列出全部功能；每个用户能感知的功能一页，先挑最重要的三到五个。每页按 [功能页示例](references/feature-example.md) 的四节写：子功能（带编号，工单的【实测】引用它）、用户从哪里进入、怎么驱动（每个动作配确切命令和可观察的结果）、坑。只写用户路径、稳定抓手、前提状态、命令和可观察的证明，不写实现细节。地图列了几个入口，证明就要覆盖几个。

4. **照它实跑一次。** 启动、自检、驱动一个功能、取证、收拾现场；收拾之后确认证据还在写明的位置。哪步失败就改正文再跑，每次失败后也要跑一遍收拾现场，不留进程和端口。没实跑过的验证入口是草稿。

5. **接上入口。** 仓库 `AGENTS.md` 加一行：实测按 `docs/verification/<产物>/README.md`，功能编号见同目录的 `features/`。

完成标准：`README.md` 六节都有、没有占位；三到五个功能页；实跑一遍的证据路径写进汇报，收拾后证据仍在。

## 维护

功能改了、【实测】照地图走不通，或者隔一段时间核对一次时做。结果三选一并写明：**干净**（每个功能都对照过源码、实跑过，没有要改的）、**有改动**（改动只含实跑证明过的修正）、**受阻**（覆盖没做完，或者证明过的修正不能安全交付，写清卡在哪）。

只改验证入口自己的目录（`README.md`、`features/`、它带的脚本），不改产品代码：地图写的行为产品已经不做了，要么是说明过时（改地图），要么是产品坏了（报告，不在地图里掩盖）。

1. **索引**：`features/README.md` 的列表和目录里的文件一一对上，补缺、删多、去重。
2. **对源码**：每个功能页对照源码，看入口和行为有没有漂移，带出处记下；每页产出一句用户视角的功能说明、源码入口、可能的漂移、一个实跑办法。功能多时按功能分给几个只读的执行者并行读，它们不驱动产物、不改文件。再看最近的改动里有没有地图漏掉的用户入口，要指出具体源码路径才算漏掉。
3. **实跑**：源码看着干净也要做。按 `README.md` 的启动方式，每个功能至少驱动一次，全程守住三条：驱动前自检，出过意外再自检或重启到已知状态；取到的证据在每次收拾现场后仍在原位；驱动启动的东西用完就停，失败留下的残余也清掉。自检失败是因为说明漂移的，按漂移修好重试一次，仍不行就判受阻。到不了的功能，写明缺的前提（权限、系统、外部状态）和试过的路径；地图没写这个前提，就是漂移。
4. **归类**：说明错或缺 → 改地图；产品能用但驱动不了 → 修脚本，修完重新实跑；产品真坏了 → 记下交给用户，不进本次改动。
5. **交付**：有改动时，交付前重读每个改过的文件；干净或受阻只报告结果和覆盖情况。

完成标准：每个功能页都有源码对照和至少一次实跑，结果是三种之一，漂移和产品问题分开列出。
